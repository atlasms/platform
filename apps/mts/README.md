# @atlas/mts

The Media Transcoding System — FFmpeg, supervised. Queue-driven: a command or a request becomes a
job row, a worker leases the row, runs FFmpeg once per preset, checksums each output, and announces
what it made. Design: [`docs/architecture/services/mts.md`](../../docs/architecture/services/mts.md);
contract: [`mts.yaml`](../../docs/architecture/openapi/mts.yaml).

Generated by `nx g @atlas/generators:service mts --db --broker` ([what that gives you and why](../../tools/generators/README.md)).

## What is built (EP-16, first slice)

**16.1** the command consumer and the job table · **16.2** FFmpeg orchestration with cancellation ·
**16.3** the built-in presets (`proxy`, `thumbnail`, `audio-proxy`, `broadcast`) · **16.5** `transcode.completed`
with per-rendition sha256, `transcode.failed` · and, partly, **16.4**: progress is parsed and kept on
the job (`percent`), not emitted as `transcode.progress` — see below.

**Not built:** `transcode.progress` events (16.4), the profile registry and `GPU` selection (16.6),
`ingest.accepted` → automatic proxy+thumbnail (needs EP-15.5), editor renders.

## The queue is a table, not the broker

`transcode.job.create` arrives once and is acknowledged in milliseconds — it becomes a `queued` row
in the same transaction as its seen-mark (a redelivery is a `duplicate`) and its audit record. What
happens afterwards — leased, retried, resumed after a crash, read by `GET /jobs/{id}` — is state, and
state that lived only as an unacked broker message could not be read, counted or resumed. The worker
spends minutes in FFmpeg; a consumer that encoded inside the message handler would have its message
redelivered mid-encode by any sane ack deadline. So: the broker delivers the command, the row is the
job ([`jobs.ts`](src/jobs.ts)).

**Leasing is a compare-and-set.** `putJob(job, ifState)` writes only if the row is still in the
state it was read in, so two workers that read the same row cannot both run it — the conformance
suite races them. One job at a time per process: FFmpeg already uses the cores it is given, and the
design's elasticity is more pods, not more concurrency per pod.

## What is retried, and what is not

The distinction the whole failure path rests on comes from the encoder port
([`transcoder.ts`](src/transcoder.ts)):

| Outcome                       | Meaning                                                    | The job                                                                                     |
| ----------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| an output                     | the file exists; it is checksummed (streamed, sha256)      | the next preset; `completed` with `transcode.completed` after the last                      |
| `TranscodeRefusal`            | FFmpeg READ the input and refused it, or produced nothing  | `dead-letter` at once, `transcode.failed` (`TRANSCODE_REFUSED`) — no retry makes bytes good |
| anything else                 | the tool or the machine: a missing binary, a kill, no disk | `failed` with a `retryAt` (30 s, doubling, capped at 10 min); `dead-letter` after 3         |
| a drain (the pod is stopping) | interrupted, not tried and found wanting                   | back to `queued`, **the attempt returned** — a rollout is not charged against a job         |

`failed` is the waiting room, not a terminal state: a failed job is leased again once its backoff has
passed. `transcode.failed` is emitted when the platform has **given up**, not per attempt — mts.md
points it at Notifications, and a notification per retry is a pager that gets muted.

A worker that dies holding a job leaves it `running`; the loop's sweep takes back any `running` row
nobody has written for `ATLAS_TRANSCODE_STALE_MS` (mts.md's visibility timeout), attempt returned.

Classification by FFmpeg's words is unpleasant and version-dependent, so the refusal patterns are
narrow and the **default is retry**: mistaking a machine fault for a bad file dead-letters work that
would have succeeded, which is the more expensive error. Two rules do not depend on prose at all: a
zero-length or missing output is a refusal (FFmpeg exits 0 having written nothing when a video preset
meets an audio file), and `out_time_ms` is read as **microseconds**, which it is despite its name.

## Where inputs come from — until HSM

HSM (EP-14) is meant to resolve paths; it does not exist. So a job's `inputPath` must be inside MTS's
**work root** (`ATLAS_MTS_WORK_DIR`, a PVC of its own), and outputs are written under
`renditions/<jobId>/<preset>.<ext>` — named by job and preset, so a retry overwrites its own output
rather than accumulating one per attempt (mts.md's idempotent output naming). The containment test is
on the RESOLVED path, so `..`, an absolute path elsewhere and a sibling that merely shares a prefix
(`/work-other`) are all refused; over HTTP, a missing input is refused too (a 422 now rather than
three attempts and a dead letter later). A broker command may name a file HSM is still placing, so
that path waits for it through the retry instead.

Two consequences, both temporary and both stated in the manifest: **one replica** (the work area is
ReadWriteOnce), with a `Recreate` rollout so the new pod is not waiting on the old one's volume; and
the dev overlay renders a sample clip into the work area (`infra/k8s/overlays/dev/mts-sample.yaml`),
because nothing else in a cluster can hand MTS an input — RIM's staging area is its own volume and a
staged path never leaves RIM.

## Authorization

`asset:write` on the **`files`** field group to enqueue, `asset:read` on it to read a job —
renditions are the file set, the Librarian's half (authorization-model.md §3.1), and it is the grant
MAM's `GET /assets/{id}/files` asks for. `canEnforce`, strict, with the context MTS has: the channel
and the group. It does not have the asset's category, so a writer narrowed to a category subtree is
**refused** rather than let through; that writer's transcodes arrive as broker commands from the
service that knows the asset. A broker command is the platform's own write and is not authorized per
user. Another channel's job is 404.

## Progress

Parsed from FFmpeg's `-progress pipe:1`, scaled across the job's presets, and written to the row —
not emitted. `transcode.progress` is best-effort by contract, and putting a per-tick broadcast through
the outbox (durable, ordered, audited) would make a progress bar cost what a domain event costs. A
progress write that loses its compare-and-set is dropped: progress about a job that already finished
is noise. `GET /jobs/{id}` is what a progress bar polls.

## The presets

| Id            | Kind        | Needs | Output                                                                                            |
| ------------- | ----------- | ----- | ------------------------------------------------------------------------------------------------- |
| `proxy`       | `proxy`     | video | H.264 ≤720p (even height), AAC 128k, MP4 with the index first (`faststart`)                       |
| `thumbnail`   | `thumbnail` | video | one JPEG at 360p, FFmpeg's shot selection rather than frame 0 (a slate)                           |
| `audio-proxy` | `proxy`     | audio | AAC 128k in M4A                                                                                   |
| `broadcast`   | `broadcast` | video | XDCAM HD422-class: MPEG-2 4:2:2, 50 Mb/s CBR, 1920×1080 (letter/pillarboxed), PCM 24/48, MXF OP1a |

The broadcast rendition is the one that goes to air. MPEG-2 4:2:2 in MXF is what playout servers
ingest natively and what FFmpeg writes without a licensed codec — which an air-gapped install
cannot fetch. It deliberately does **not** conform the frame rate (MXF refuses a rate no broadcast
format uses, and that is a refusal of the input; conforming to a channel's house rate is the
profile registry's, 16.6), does not interlace, and stamps no XDCAM fourcc — the fourcc names a
rate and scan type, and a 1080i50 tag on a 1080p25 file is a lie a playout server believes. The
real-binary test reads the output back with ffprobe: the claim is about the bytes.

CPU-only, deliberately: a built-in set that assumed a GPU would fail on every machine without one,
including CI. NVENC/QSV/VAAPI belong to the profile registry (16.6).

## Tests

- **Conformance** ([`store-conformance.ts`](src/store-conformance.ts)), driven through the service
  with a real work directory, on sqlite and — in CI — Postgres: enqueue and its refusals, a run with
  real checksums and both events, the lease race, priority then age, refusal → dead-letter, tool
  failure → backoff → dead-letter, a drain returning the attempt, the stale sweep, the broker
  command's idempotency and refusals, authorization, channel scoping.
- **The real FFmpeg** ([`transcoder.test.ts`](test/transcoder.test.ts)) on clips it generates: every
  preset, a non-media file refused, a video preset on audio refused, cancellation killing the process
  promptly, a missing binary a tool failure. Skipped without the binary on a laptop; **failed** in CI
  without it (the workflow installs it).
- **Smoke**: a real transcode on the cluster, through the gateway, into MAM's file rows with the same
  checksums — the first time the FileRef mirror (EP-17.8) ran against a real producer.

## Run

```sh
npx nx test @atlas/mts        # in memory; the FFmpeg tests need ffmpeg on the PATH
npm run k8s:up                # builds atlas/mts:dev WITH ffmpeg (APK_PACKAGES) and deploys it
kubectl -n atlas logs deployment/mts -f
```

| `ATLAS_TRANSCODE_TIMEOUT_MS`   | `1800000` (30 min)                 | Per output; past it the attempt is killed and RETRIED     |
| `ATLAS_TRANSCODE_MAX_ATTEMPTS` | `3`                                | Before a tool failure is dead-lettered                    |
| `ATLAS_TRANSCODE_STALE_MS`     | `300000` (5 min)                   | A `running` row unwritten this long is a dead worker's    |
