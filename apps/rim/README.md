# @atlas/rim — Recording & Ingest Manager

The entry point: brings media in — chunked uploads (EP-15.1, this), watched folders and recorders
(EP-15.2, later) — and decides whether it is accepted (EP-15.3). Design:
[rim.md](../../docs/architecture/services/rim.md) · contract:
[`rim.yaml`](../../docs/architecture/openapi/rim.yaml).

Generated by `nx g @atlas/generators:service rim --db --broker` and then given its domain. What the
scaffold provides is in [`tools/generators/README.md`](../../tools/generators/README.md).

## The upload (EP-15.1; FR-ING-2)

**The server sizes the parts.** `POST /uploads` answers with `partSizeBytes` (8 MiB,
`ATLAS_UPLOAD_PART_BYTES`) and `partCount`; the client slices the file that way. Every part but
the last is exactly that long, the last is the remainder, and a part of any other length is
refused (422) _before_ it is stored — so the assembled file is `sizeBytes` long by construction,
and a client that sliced wrongly finds out at the first part, not at completion. Bigger than any
part may be is a **413**, from Fastify's cap on the octet-stream parser, translated into the
taxonomy rather than filed as a server failure.

**Resumable.** A part may be sent again — a retry, a resume — and the last write wins.
`GET /uploads/{id}` says which parts the server holds; a client that lost its connection sends
the rest. `POST /complete` with a hole is a **409** whose `details.missing` lists the holes.

**Completion assembles once, in part order, hashing on the way**, so the job's `checksum` is of
the bytes actually written, not of what the client claimed. The received file stays in staging
for HSM to place (EP-14; RIM never writes storage — FR-HSM-5); the parts are removed. The job,
`ingest.detected` and the `audit.recorded` delta commit in **one transaction**, after the bytes
are on disk. Completing twice returns the same job: the client that asks again is the one whose
first answer was lost.

**What is atomic and what is not.** A part is two writes that cannot share a transaction —
bytes to the staging area, a row to the store — and the ORDER makes that safe: file first, row
second. A crash between the two leaves a part on disk that no row records, which a resume
overwrites; the other order would leave a row promising bytes that are not there, and completion
would assemble a hole.

|                                      |                                                                            |
| ------------------------------------ | -------------------------------------------------------------------------- |
| `POST /api/v1/uploads`               | `{ filename, sizeBytes, contentType? }` → 201 with the part size and count |
| `GET /api/v1/uploads/{id}`           | the upload and `received: [n…]` — what a resume answers from               |
| `PUT /api/v1/uploads/{id}/parts/{n}` | the raw bytes, `application/octet-stream` → 204                            |
| `POST /api/v1/uploads/{id}/complete` | → 202 with the `IngestJob` (state `detected`); idempotent                  |
| `DELETE /api/v1/uploads/{id}`        | abandon; parts and row go                                                  |

`ingest:write` for all of it, `canEnforce` with the channel. Another channel's upload is a
**404**, not a 403. A file name is a name, not a path: separators, `..` and control characters
are refused rather than cleaned. The received path never crosses the wire.

**Staging** (`ATLAS_RIM_STAGING_DIR`) is a volume of this pod's — the one place a read-only root
filesystem lets it write — and is not the asset store: a PVC so a half-received upload survives a
pod restart, no replication because what matters is handed to HSM. An open upload not completed
within `ATLAS_UPLOAD_TTL_MS` (24 h) is **swept**, parts and row, on `ATLAS_UPLOAD_SWEEP_INTERVAL_MS`.

**Through the gateway**, a part is the one body on this platform larger than the 1 MiB JSON cap;
the `/api/v1/uploads` prefix carries its own (`ATLAS_UPLOAD_BODY_LIMIT_BYTES`, 8 MiB) rather than
the gateway raising the cap everywhere. `/api/v1/ingest` is not routed until EP-15.6.

## The store is a port, with two adapters and one suite

`RimStore` — `sqliteRimStore` for tests, `pgRimStore` for production — held to
`rimStoreConformance`, run against **both** in CI. Uploads and jobs are JSON documents with the
queried columns alongside (channel, state, expiry); parts are **rows** keyed by `(upload, n)`,
because "which parts do I hold" is the question a resume asks and a row answers it without reading
the disk. The suite is driven through the service with a real staging directory: a part refused
before it is stored, a resume answering from what was accepted, the last write winning, assembly in
part order with the checksum of those bytes, the job and its events committing together,
completion idempotent, another channel's upload not found, the sweeper taking only what expired.

## Run

```sh
npx nx test @atlas/rim                                                       # sqlite double + a temp dir
ATLAS_PG_URL=postgres://atlas:atlas@localhost:55432/atlas npx nx test @atlas/rim   # + Postgres
npm run k8s:up && npm run smoke      # an 8 MiB part through the gateway, resumed, hashed, audited
```

| Variable                           | Default                                    |                                                  |
| ---------------------------------- | ------------------------------------------ | ------------------------------------------------ |
| `ATLAS_PG_URL` / `ATLAS_PG_SCHEMA` | `postgres://…@postgres:5432/atlas` / `rim` | waited for at startup, within 120 s              |
| `ATLAS_NATS_URL`                   | `nats://nats:4222`                         | the outbox relay; retried, never readiness       |
| `ATLAS_IAM_ORIGIN`                 | `http://iam:3000`                          | critical readiness dependency; the policy client |
| `ATLAS_RIM_STAGING_DIR`            | `/var/lib/atlas/rim/staging`               | created at start; a volume in k8s                |
| `ATLAS_UPLOAD_PART_BYTES`          | `8388608`                                  | must fit the gateway's cap on `/api/v1/uploads`  |
| `ATLAS_UPLOAD_TTL_MS`              | `86400000`                                 | an open upload older than this is swept          |
| `ATLAS_UPLOAD_SWEEP_INTERVAL_MS`   | `60000`                                    |                                                  |
