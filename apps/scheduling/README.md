# @atlas/scheduling — the program table

The reel per channel per broadcast day — ordered items with materialized starts, fixed anchors,
one-level live sub-schedules — and, in v1, validation and the send-to-air hand-off. EP-18 v0.
Design: [scheduling.md](../../docs/architecture/services/scheduling.md) · the model:
[data-model.md §3](../../docs/architecture/data-model.md#3-the-schedule-aggregate) · contract:
[`scheduling.yaml`](../../docs/architecture/openapi/scheduling.yaml).

Generated by `nx g service scheduling --db --broker` and then given its domain. What the scaffold
provides is in [`tools/generators/README.md`](../../tools/generators/README.md); this is the reel.

## The one design decision that shapes everything: the write path is THIN

> The backend does **not** hard-block overlaps or gaps. — data-model §3.4, §3.6; FR-SCH-9

The **editor** maintains the reel: reflow between fixed anchors, no overlaps, gaps flagged. This
service persists the `start`s the editor computed and stores `end = start + duration` alongside
them so the control-room reads are index hits. Overlap and gap detection is v1's
`POST /schedules/{id}/validate`, **on demand** — never a gate on save. A test saves a reel with an
overlap and asserts it was stored.

What the service _does_ refuse is a reel that cannot be stored or read back as one — the shape of
the aggregate, not editorial judgement:

| Refused (422)                                               | Because                                    |
| ----------------------------------------------------------- | ------------------------------------------ |
| a duplicate `seq` in one reel or one sub-reel               | order is undefined                         |
| a `live` item with a `mediaId` / a `media` item without one | §3.3, §3.5                                 |
| a `parentItemId` that is not a live item in this reel       | §3.5                                       |
| a sub-schedule inside a sub-schedule                        | nesting is exactly one level (§3.5)        |
| a second schedule for the same channel and day              | one program table per broadcast day (§3.1) |

The same rules apply at the wire (`parseItemInput`, which names the bad row: `items[7]: …`) and in
the service (`checkReel`), so no entry point can skip them.

## The API (v0)

|          |                                               |                                                                                                             |
| -------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `GET`    | `/api/v1/schedules?broadcastDate&after&limit` | the channel's tables, newest day first, keyset on id                                                        |
| `POST`   | `/api/v1/schedules`                           | create a day: `{ broadcastDate, timezone, notes? }` → 201, or 409 if the day exists                         |
| `GET`    | `/api/v1/schedules/{id}`                      | the header **with its reel**, in reel order                                                                 |
| `PATCH`  | `/api/v1/schedules/{id}`                      | `timezone`, `notes`. `state` is not writable here — it moves through validate and send-to-air (v1)          |
| `GET`    | `/api/v1/schedules/{id}/items`                | the reel: top-level by `seq`, each live item followed by its sub-reel                                       |
| `PUT`    | `/api/v1/schedules/{id}/items`                | **the editor's save** — the whole reel, as given; ids kept where sent, minted where not                     |
| `POST`   | `/api/v1/schedules/{id}/items`                | append one item                                                                                             |
| `PATCH`  | `/api/v1/schedules/{id}/items/{itemId}`       | change one; validated as the **merged** item, so a media item cannot become live without dropping its media |
| `DELETE` | `/api/v1/schedules/{id}/items/{itemId}`       | remove one — and its sub-schedule if it is a live item                                                      |

`schedule:read` for reads, `schedule:write` for writes, `canEnforce` with the channel. Another
channel's schedule is a **404**, not a 403 — a 403 would confirm it exists.

## Every write goes out through the outbox, twice

In the same transaction as the rows: `schedule.updated` (`scheduleId`, `state`, `itemCount`) for
consumers — Integration's EPG feed, the WebSocket fan-out — and `audit.recorded` with the
field-level delta (EP-19.2, AGENTS.md §5.6). The header's fields diff on their own; the reel change
rides in the delta as `items` (a save) or `items.<id>` (one item), supplied by the caller because
the rows are not on the header. `revision` is the schedule's `version`, bumped on every write to
the header **or** the reel. A no-op `PATCH` — UIs submit whole forms — changes nothing and emits
nothing.

The relay pipelines different subjects concurrently (EP-03.7), so `schedule.updated` and
`audit.recorded` may interleave on the wire; each subject's own order is what is promised, and the
conformance suite asserts exactly that — it caught a test that assumed a global order.

## The store is a port, with two adapters and one suite

`ScheduleStore` — `sqliteScheduleStore` for tests, `pgScheduleStore` for production — held to
`scheduleStoreConformance`, run against **both** in CI. Schedules are JSON documents (the header
changes shape as v1 adds validation and export state); items are **columns**, indexed on
`(channel, broadcast day, start)` and `(channel, start, end)` per §3.6, so `onAir(channel, from, to)`
is a range scan. The suite is driven through the service and proves the unit of work: a reel replaced
atomically with its events, ids preserved across a save, overlaps _not_ refused, the aggregate's
invariants refused, the on-air read, and — found by the suite — **a header write leaves the reel
intact**: sqlite's `INSERT OR REPLACE` is DELETE + INSERT, and the items cascade on delete, so a
`PATCH` to the notes wiped the reel on the test double while Postgres kept it. Both adapters upsert
now.

## Not yet (v1 — EP-31)

Validation (`POST /validate`: gaps, overlaps, fixed anchors, rights, rendition availability),
the approved-only guard at serialization, the pluggable playlist serializer (Cinegy MCRList first),
`POST /send-to-air`, export profiles, the copy-a-range operation (§3.7), schedulability intake
from MAM's lifecycle events. The reference slice in `reference/scheduling-service/` proved the
guard and the intake; it is lifted, not copied — it uses constructor parameter properties, which
the containers' strip-only loader refuses.

## Run

```sh
npx nx test @atlas/scheduling                                              # sqlite, in memory
ATLAS_PG_URL=postgres://atlas:atlas@localhost:55432/atlas npx nx test @atlas/scheduling   # + Postgres
npm run k8s:up && npm run smoke      # creates a day, saves a reel with an overlap, reads it back, finds it in the audit history
```

| Variable                  | Default                            |                                                    |
| ------------------------- | ---------------------------------- | -------------------------------------------------- |
| `ATLAS_PG_URL`            | `postgres://…@postgres:5432/atlas` | waited for at startup, within a 120 s budget       |
| `ATLAS_NATS_URL`          | `nats://nats:4222`                 | the outbox relay; retried, never a readiness check |
| `ATLAS_IAM_ORIGIN`        | `http://iam:3000`                  | critical readiness dependency; the policy client   |
| `ATLAS_RELAY_INTERVAL_MS` | `1000`                             |                                                    |
